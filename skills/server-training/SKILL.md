# 科研训练与证据驱动迭代

## 工作模式与边界

- 先确认当前是研究构思、实验规划、启动、进度检查、诊断恢复还是结果复盘。进度查询不自动扩展为文献综述、参数搜索、重新启动或追加实验。
- 以形成可检验的新方法和可靠研究结论为目标；挑战明确协议下的强基线与 SOTA，不把“多跑几个配置”当作研究进展，也不承诺必然超过 SOTA。
- 先读取当前项目的研究问题、评测协议、已有实验和资源约定。项目特有规则优先；缺少足以改变实验正确性的信息时先补齐，独立的文献和代码分析可继续。
- 候选方案不等于执行授权。在获批研究范围、资源预算和停止条件内主动推进；增加费用、扩大研究范围或改变已约定的评测协议前重新确认。未经授权不占用服务器、上传数据或启用付费服务。
- 主机、磁盘和 SSH 定位按需使用 `server-cluster`；实际修改代码时使用 `code-development`，优先实现能检验机制的最小改动。个人技能与项目研究知识的维护遵循现有分层授权。

## 研究循环：先解释问题，再决定训练什么

1. **盘点已有证据。** 核对当前强基线、代码与配置、划分、学习曲线、误差切片、失败运行和计算成本。将论文结论、实现事实、实际观测和解释假设分开；用程序聚合完整结果，不从零散日志猜总体表现。先说明当前瓶颈和缺失证据。

2. **从论文中找机制。** 结合可访问的论文库和项目阅读记录，先查同问题的近邻研究、强基线及反例，再用去掉领域专名的结构性问题检索相邻领域。关键依据实际阅读论文方法、实验或官方实现，记录出处与适用条件；只有摘要时明确证据边界。未检索到相同方法不能证明新颖性。

3. **形成有区别的候选。** 每个候选说明：已观察到的瓶颈、借鉴来源、作用机制、具体改动、关键预测、竞争解释、反驳条件和成本。区分复现、机制诊断与创新候选；创新候选须说明相对最近邻工作的实质差异，直接使用已有方法或组合不自动构成创新。组合方法时说明信息或优化上的联系、假设是否兼容、预期互补与新增代价；不只把模块名字拼在一起。候选应体现不同机制，不为凑数量改写同一个想法。

4. **先做有判别力的实验。** 比较候选的证据支持、区分解释的能力、潜在研究价值及成本。先选能排除关键疑点的低成本试验，再决定是否扩大训练。保留强基线和必要对照；需要联合改变多个因素时说明原因，用合适消融区分贡献，不机械要求所有研究只能单因素变化。

5. **用结果改变方向。** 每个实验或批次结束后先判断运行与干预是否有效，再区分“证据不足”“支持假设”“削弱或反驳特定假设”“预算停止”。单次不涨分、短跑未收敛或区间过宽不能直接否定方法家族；分数上涨也不能自动证明所声称的机制。记录结论适用范围和重新考虑条件。

6. **主动综合，而非继续排队。** 有支持时，强化机制验证、适用边界和规模验证；关键预测失败时，修改或淘汰对应解释。出现收益停滞、共同失败模式或反常结果时，回到论文与候选空间，提出深化、拓展、转向或停止的理由。不在缺少新依据时只换下一组 seed 或微调参数维持旧方向。

## 实验价值与公平性

- 多 seed 用于估计不确定性、失败率和稳健性；有依据的超参数搜索用于公平比较、复现或机制检验。预先说明搜索范围、预算和选择规则，不挑幸运 seed，不把调参本身包装为方法创新。
- 不默认采用双分支、教师学生、蒸馏、融合或其他固定模板。采用时必须说明当前问题需要什么信息、监督或优化作用，并用对照核对收益是否仅来自额外容量、数据、预训练或计算。
- 固定数据版本、独立实验单位、训练／验证／测试用途、主要指标及 checkpoint 选择规则。目标测试结果不反向用于未声明的方法或参数选择；已有测试反馈被用于开发时，明确其探索性质并保留独立确认途径。
- 区分执行有效、实现符合假设、统计证据与科学贡献。无效运行先修复或隔离；可靠负结果用于减少无价值投入，不把预算不足或实现错误写成科学反证。资源有限时如实降低结论强度。
- 用可比协议、合理调优的强基线和不确定性支撑比较，同时报告数据、模型容量、搜索与训练／推理成本差异。SOTA 是有日期和范围的结论；不可比时只报告本次协议下相对所复现基线的结果。

## 执行、恢复与运行证据

- 启动前确认批准的实验／批次、run ID、主机、GPU、实际配置、预算与停止条件；核对真实进程、资源归属、数据和输出路径。权限不足或归属不可见时标未知，不据此认定空闲。保留他人训练与旧产物。
- 按任务做必要预检与最小链路试跑；单机不默认套用 NCCL、Slurm、共享盘或故障注入清单。分布式、恢复链或训练状态结构改变时再检查相应分支。
- 训练前按项目约定提交本次相关代码与配置，关联实际分支、提交号和最终生效配置。Git 操作细则按 `code-development` 的 Git 条款执行，仅在实际需要相关操作时选读；无仓库时先明确版本记录方案。
- 长任务使用服务器已有的稳定运行方式。记录任务标识、实际命令、工作目录、GPU 与首条有效训练日志；分别报告“命令已发出”“已取得任务标识”“已确认运行”“已确认完成”，每一状态都须有对应证据。
- SSH 断连或响应不明时先标状态未知，按实验标识核对进程、配置及近期日志；未确认状态前不重发启动命令。任何重试仍在原批准范围内。
- 长任务明确 checkpoint、保存完成语义及可接受返工范围。区分权重初始化、近似续跑和完整状态恢复；按框架与算法核对所需状态和恢复连续性，不把文件存在或成功加载当成恢复正确。
- 检查有效步数、学习信号和必要性能指标。诊断先找可区分根因的证据，不自动调参、换算法或重启；故障修复若改变有效 batch、精度、采样或预算，记录并重新判断实验可比性。

## 收尾与下一步

- 核对进程退出、末尾日志、实际配置、结果文件与必要指标；退出码、会话消失或文件存在都不能单独证明成功。失败和中止也保留必要证据，标明不完整产物。
- 沿用项目现有实验记录，关联假设、run ID、代码与数据版本、配置、预算与实际消耗、选择依据、结果和产物。按 Git 约定提交本次结果摘要；权重与大数据不强制入 Git，不生成无人使用的校验文件或新管理系统。
- 交付说明本轮学到了什么、哪些方向被支持或削弱、哪些仍未决、下一步最有判别力的动作及所需预算。只有满足前置条件且已获批的实验才能接续；不得因结果不理想无限追加训练。
