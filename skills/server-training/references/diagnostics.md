# 训练异常的证据诊断

读取时机：发生明确异常，或有效进度、学习信号、吞吐与预期不符。诊断目标是区分根因并恢复可解释的实验，不是遇到症状就换参数。

## 通用顺序

1. 确认 run、代码、配置、时间、训练阶段及相关节点／rank，保留失败前后原始日志位置。
2. 核对各 rank 的 run、训练 step、时间基准和本地事件顺序，找首个可解释异常及其后果；日志缓冲或节点时钟差异可能改变打印顺序，不能只按跨节点时间戳排序就认定根因。
3. 先核对输入、实现、资源和评估链是否有效，再决定能否评价科研假设。
4. 采取授权内能区分解释的最小检查或修复；改变科学比较条件时单独记录，必要时作为新配置重验。

## 症状表

| 症状 | 最小只读检查动作 | 应读取或比较的证据 | 优先处理与边界 |
| --- | --- | --- | --- |
| GPU OOM／进程被杀 | 从本次 run 的首个相关异常向前查看输入形状和阶段，核对对应进程及其他 rank 的内存记录 | 各 rank 的分配／保留／峰值显存、batch；主机内存或 cgroup／调度器记录 | 区分 GPU 容量、碎片、激活、临时 workspace 和主机内存；不要仅凭退出码归因为 OOM。改 batch、精度、累积或并行方式后核对有效训练条件 |
| NCCL 超时、barrier 等待 | 对齐 run 和 step，分别追溯各 rank 内部首个异常，再结合时间基准与进程／任务步骤状态检查错误传播 | OOM／I/O／导出失败、rank 是否存活、world size 与拓扑配置、时钟和日志缓冲差异 | 最早打印的错误只是线索；先处理有因果证据的失败，避免只调大超时或反复重启，确认通信问题后才做对应检查 |
| loss NaN／Inf 或梯度异常 | 定位第一个非有限 step，对比前后已记录的数据范围、分项损失、梯度、scaler 和学习率 | 标签、输入及损失范围、更新顺序、最近代码与配置差异 | 区分数值、数据和实现原因；不默认用 nan_to_num、跳 batch 或裁剪掩盖问题。确有算法需要的稳定化作为明确改动记录 |
| 无输出或似乎挂起 | 比较最后有效 step、日志与产物更新时间，查看进程状态及最近阶段，确认是否只是缓冲未刷新 | 数据加载、初始化／保存阶段、日志缓冲及各 rank 栈信息（权限允许时） | 无输出不等于死锁；未明确归属与中断授权不终止进程。现有证据不足时说明还缺哪项观测 |
| GPU 利用率低／数据饥饿 | 对照已有分步计时，比较数据等待和计算耗时；同时查看对应 CPU、I/O 与数据加载进度 | 数据处理、批大小、缓存状态及不同阶段的利用率 | 定位瓶颈后调整当前链路；不默认增加 worker、换存储或改模型。缺计时时先提出最小观测方案 |
| 吞吐下降／显存持续增长 | 选相同训练阶段与输入形状的记录区间，比较 step 时间和内存走势，并对齐评估、保存及数据切换事件 | 日志、图保留、数据变化、预算及阶段差异 | 区分正常阶段差异与回归；执行加速不自动等同方法效果提升 |
| 验证提升但独立评估异常 | 对照两次评估的生效配置、划分和预测／标签样本，检查预处理拟合范围与指标聚合 | 重复样本、eval mode、标签映射、checkpoint 及阈值选择 | 先检查泄漏或协议变化；不能直接归因为泛化机制，也不能择优更换测试规则 |
| RL 奖励上升但任务质量不变 | 抽查已保存的生成／轨迹及逐项奖励，和真实成功率对照，核对终止规则与评估归一化 | 奖励实现、parser、终止原因、评估环境与输出质量 | 检查奖励投机和任务目标错位；单一 reward 或 loss 不能证明能力提升 |
| 恢复后指标突变／步数异常 | 用框架支持的只读元数据或加载日志核对来源、步数和实际恢复状态，再对照恢复前后记录 | 优化器／调度器／scaler、RNG、数据游标、replay／归一化及保存完成证据 | 某个键存在不等于状态已恢复；不执行不可信序列化代码来检查文件。缺状态时标近似续跑或新 run，不并入原公平对照 |

多节点日志中的后续通信超时常需结合先前节点失败解释；NVIDIA 的多节点 Skill 可提供定位思路，但其框架、容器和节点布局不能成为通用前提。[NVIDIA Multi-Node Slurm](https://docs.nvidia.com/nemo/megatron-bridge/0.7.0/skills/nemo-mbridge-multi-node-slurm/SKILL.html)

退出状态的含义取决于 shell、调度器和任务步骤。Slurm 将退出码与终止信号分别记录，并可能出现脚本返回成功、内部步骤失败的情况；应结合原始日志及任务步骤状态，不使用“1 一定是 Python 错误、9 一定是 OOM”等固定映射。[Slurm Job Exit Codes](https://slurm.schedmd.com/job_exit_code.html)

性能修复也需要防止错误归因：NVIDIA Memory Tuning 的记录曾根据后续证据纠正 OOM 修复因素的解释。可借鉴复查配置与混杂的方式，不能复制其特定硬件上的数值和参数作为默认答案。[NVIDIA Memory Tuning](https://docs.nvidia.com/nemo/megatron-bridge/0.7.0/skills/nemo-mbridge-perf-memory-tuning/SKILL.html)

## 诊断结果交接

报告已确认事实、仍可能的解释、已做检查、下一项能区分解释的动作，以及是否影响原实验有效性。修复导致有效 batch、数据、精度、采样或预算变化时，更新实验记录和比较范围；不把运行失败写成方法失败。
