# 运行预检、实验记录与恢复

读取时机：新训练启动、重要配置或规模变化、checkpoint 策略变更、恢复长任务。例行进度查询沿用已验证约定。

## 预检按实际形态分层

| 范围 | 必要证据 |
| --- | --- |
| 所有新 run | 批准的实验／预算／停止条件，实际代码和生效配置，数据版本与划分，输出根可用且容量足够，run ID 唯一，是否新训或恢复明确 |
| GPU 训练 | 真实进程与资源归属、可用设备及绑定、相关环境与关键框架版本；新链路以最小训练—验证—保存过程确认可运行 |
| 分布式或规模变化 | world size、rank 映射、配置与数据一致性、通信及必要存储可见性；按问题运行最小通信或全规模短测，不对单 GPU 默认执行 NCCL 检查 |
| Slurm／容器 | 真实分区和资源限制、时间限额、挂载与执行环境、任务步骤日志；不假设任何服务器都具备这些工具 |
| 高代价长任务／新恢复链 | 保存完成状态和恢复连续性有验证；已知不稳定硬件再针对 XID、ECC 或系统记录排查，不将全面硬件审计作为每次试跑前提 |

少量样本试跑应覆盖数据读取、目标计算、参数更新与必要评估；按任务检查形状、标签、损失、梯度或奖励是否合理。成功启动不是实现符合论文的证明，机制检查仍由对应实验负责。

数据和产物放在项目已确认、持久且容量合适的位置。只有实际需要多节点共用时才要求共同可访问路径；不要为一次训练搬迁存储、重建环境或统一框架。

## 最小运行记录

沿用现有 CSV、JSONL、实验管理器或项目记录。每个 run 关联：假设／批次 ID、代码 commit、最终配置、数据与划分、关键环境版本、种子、训练和搜索预算、选模规则、实际命令／主机／任务标识、日志与 checkpoint 路径、状态与结果。

预算与实际消耗分别记账，字段并入上述记录，不新建成本平台：

| 字段 | 记录口径 |
| --- | --- |
| 实际运行时长 | 记录训练实际占用的开始／结束时间或累计时长，排队时间单列；运行中注明截至时间与估计值 |
| GPU 类型与数量 | 记录实际型号、数量及分配变化；CPU 任务记录运行时长与相关 CPU 配置，不硬填 GPU 卡时 |
| 实际 GPU-hours | 按分配区间累计“GPU 数量 × 占用小时”；区分分配／计费占用与有效计算，不能用平均利用率随意折算 |
| 实际费用 | 仅在有计费信息时记录金额、币种及账单／费率口径；估算费用明确标为估算，未知不填零 |
| 批次累计成本与余额 | 汇总成功、失败、重试及探索／调参运行，避免把同一运行重复计入；列出批准上限、截至当前消耗与剩余额度 |

不同 GPU 型号的卡时不能直接视为等价性能或费用。比较效率时同时交代硬件、训练量与计时口径；不能只报告胜出 run 的成本而隐去失败和搜索消耗。

配置覆盖、命令行覆盖和恢复来源要反映在实际记录中，不仅保存模板。关键版本与环境声明足够时，不额外制作没人使用的“环境指纹”。不自动注册云实验服务、上传数据或权重。[W&B Skill 的运行关联设计](https://github.com/Orchestra-Research/AI-Research-SKILLs/blob/773a52944ba4747a18bd4ae9ade53fff041adcbc/13-mlops/weights-and-biases/SKILL.md)只作为结构参考，不构成使用该服务的要求。

## Checkpoint 与连续性

| 方式 | 可以声明什么 |
| --- | --- |
| 只加载模型权重，重新初始化其他状态 | 权重初始化或 warm start；不能声称完整恢复原训练状态 |
| 恢复部分训练状态，但采样、环境或数据流无法复原 | 近似续跑；记录缺失状态及对比较的影响 |
| 按框架与算法恢复所需状态，并检查连续性 | 在已验证范围内恢复训练；仍不自动保证 CUDA 位级确定性 |

需要哪些状态由实际算法和框架决定：模型、优化器、调度器、使用中的 grad scaler、随机状态、步数及数据流／sampler 位置等。优先使用框架已有机制，不为所有项目手写通用恢复系统。[PyTorch checkpoint](https://docs.pytorch.org/tutorials/beginner/saving_loading_models.html)、[AMP 恢复](https://docs.pytorch.org/tutorials/recipes/recipes/amp_recipe.html)、[StatefulDataLoader](https://meta-pytorch.org/data/main/stateful_dataloader_tutorial.html)

RL 还需核对 replay、归一化、采样器及可恢复的环境状态；梯度累积中途或 world size 改变可能破坏原连续性，需记录。不能假定保存模型就包含这些状态。

保存周期依据可接受返工时间、保存开销、配额和任务风险确定，不统一写死步数或小时。明确最近可恢复点、选模 checkpoint 和需要保留的里程碑，沿用批准的保留策略；不自动删除他人或历史实验。

恢复前核对 run、配置、数据及 checkpoint 步数；确认保存已完成。新 run 显式使用新输出位置和正确的加载配置，不靠删除旧目录获得“干净起点”。恢复后检查步数、学习率、实际更新、指标与必要状态的连续性；新链路或重要状态变化时做短恢复验证。[NeMo checkpointing](https://docs.nvidia.com/nemo/megatron-bridge/0.7.0/training/checkpointing.html)

## 启动与状态确认

使用服务器已有稳定运行方式，区分命令已发出、取得任务标识、确认运行、确认完成。SSH 不确定时先按 run ID 只读核对进程、启动时间、命令、配置和日志，不重发启动。

运行期间记录与任务相关的有效进度、吞吐、峰值显存和主要等待原因。只在出现性能问题或对应研究问题时深入 profile；监控不能只有 GPU 利用率，也不应生成无人使用的遥测体系。
