# 桌面 UI 与应用交付

适用：新建桌面应用、选择桌面框架、将原型做成可交付产品、重做 GUI、打包分发，或实现与排查安装目录选择、迁移、首次设置、自动检查及一键更新。普通 Tkinter 缺陷修复不自动触发迁移；单页知识讲解沿用适用的 HTML 技能，不为展示内容加桌面壳。

## 1. 先确定产品与实现边界

- 确认使用者、目标操作系统、最重要的操作、现有后端、数据保存方式，以及交付的是开发者工具还是普通用户安装的成品。能从项目和任务判断的自行确定；涉及平台、迁移或费用的关键缺口再澄清。
- 对需要现代桌面体验的新应用，默认优先评估 Electron + TypeScript，前端沿用项目已有 React／Vue 等方案；无现有框架时选择团队能维护的简单方案。Tauri／Wails 等仅在体积、系统 WebView、团队语言或原生集成需求确有收益时比较，不为了选型遍历所有框架。
- 现有 Tkinter 项目先判断是否真需要替换界面。已获批迁移时，保留有效业务、数据格式和后端；先做一条真实功能贯穿界面、业务与持久化，再按获批范围替换，不同时重写算法、配置系统和安装体系。
- 框架不保证视觉质量。先从用户给的截图或同类产品提炼导航、信息层次、密度和交互习惯，再设计本项目页面；不复制无关聊天框、装饰卡片、品牌素材或复杂工作台。不能以“像 Codex”推断该产品的内部技术栈。
- 版本、系统支持、包体、启动时间与内存依赖具体实现。选用受支持版本并核对官方说明，以本项目测量决定预算；不沿用博客中的通用性能数字或过时系统兼容表。

## 2. 用一条真实工作流建立 UI

按“核心任务 → 页面与状态 → 真实功能切片 → 扩展”推进。把草图或已有截图作为视觉基准即可，不另建大套设计文档。

| 设计对象 | 必须形成的实际效果 |
| --- | --- |
| 信息架构 | 用户能看出当前位置、当前对象、主操作和结果去向；按任务需要使用导航区、工作区、详情区，不强制三栏 |
| 视觉一致性 | 共用颜色、字号、间距、边框、圆角与状态色的设计变量；同类控件一致，避免逐页随意调样式 |
| 数据密度 | 大量记录优先清晰的表格、列表、搜索和筛选；关键结果易定位，说明按需展开，不把每个数字装进大卡片 |
| 操作反馈 | 根据实际功能具备空数据、加载、成功、失败和不可用状态；说明原因及下一步，不能用假数据或静默空白冒充成功 |
| 长任务 | 界面持续可交互；显示真实阶段或进度。只有后端支持时才提供有效取消，不伪造百分比或摆放无效按钮 |
| 键盘与可访问性 | 主要流程可用键盘完成，焦点可见且顺序合理；图标按钮有名称，状态不只靠颜色，文字有足够对比度 |
| 窗口与缩放 | 核对窗口变窄、长文本、滚动和 Windows 高 DPI 下的可用性；关闭、最小化与后台任务关系符合明确的产品约定 |

- 优先复用一套合适的组件库或已有组件；只有重复且稳定的需求才提炼自有组件。不为“正规开发”叠加多个组件库、全局状态框架或自研设计系统。
- 深色默认、可选浅色及 YAML 偏好按主文执行。主题使用统一变量，覆盖弹窗、表格、图表和错误状态；文字、图标、表单焦点与背景都要实际检查。
- 间距尺度、字号层级和点击区域应统一且适合目标设备。4／8 像素基准可作起点，不设所有尺寸整除、固定字号倍率或所有控件 44 像素的形式门槛。以真实可读、可点、可聚焦为准；按项目采用的可访问性标准验证。
- 快捷键、命令面板、可拖拽分栏和动画只服务于真实高频操作。保留常见键盘习惯，尊重减少动画设置，不为展示技术增加操作负担。

## 3. Electron 与现有后端的最小职责分离

- 渲染进程负责页面、交互和展示状态；主进程负责窗口、应用生命周期及受控系统操作；preload 只暴露具体业务能力。沿用这些必要边界，不再机械叠加控制器、仓储、服务工厂等层次。
- 耗时计算、训练、文件处理等放在适合的工作进程或现有后端中，不阻塞渲染进程，也不把同步重活搬进主进程后声称已解决卡顿。传递所需进度、结果及取消信号即可。
- Python 业务已可靠时优先保留，通过明确、窄小的进程通信或已有接口连接；不为了换 UI 重写模型和算法。接口覆盖必要参数、结果、失败与任务结束，避免先造通用 RPC 或插件系统。
- 如果启动本地服务，限制监听范围和调用入口，按实际威胁边界控制访问；不默认开放局域网。子进程由应用明确拥有和回收，不通过按进程名批量结束其它任务来清理。
- Python 源码开发和测试按[Python 环境与启动](python-environment-and-launch.md)使用项目开发环境。应用安装包交付 Electron 及所需的本地 Python 运行时和依赖，安装后的前后端直接从安装内容启动。使用远端服务时明确必要业务配置。

## 4. 在真实权限边界做必要防护

- 明确保持 `contextIsolation` 和渲染沙箱，渲染页面不直接获得 Node／文件系统／任意命令执行能力。不要为了省 IPC 代码关闭隔离。
- 通过 `contextBridge` 暴露具体方法，不透传完整 `ipcRenderer`、通用 shell 或任意文件读写接口。主进程在特权入口核对调用来源、所需参数及目标范围；内部已确定的同一条件不再层层重复校验。
- 对实际加载内容配置合适的 CSP，约束导航、新窗口和外部链接协议／目标；不将不可信内容当可信本地页面执行。生产资源加载按当前 Electron 官方建议及所选工具实现，不能为消除报错关闭安全选项。
- 凭据不放在渲染源码、公开配置、日志或仓库中；使用项目已有的受控保存与访问机制。安全边界是桌面进程权限带来的必要职责，不能按“反过度防御”删除，也不借此给普通内部调用新增一套验证框架。

## 5. 从源码运行走到真实安装交付

- 面向用户安装使用的应用统一通过安装程序交付。项目根目录使用 `installer/` 集中管理安装、卸载与更新的实际实现和入口，构建结果放在 `installer/dist/`。工具要求位于 package.json 等原位置的配置继续使用该入口，避免重复声明。
- Git 跟踪 `installer/` 中的源码、脚本、构建配置及必要资源。将 `/installer/dist/` 加入应用项目的忽略规则，安装包、卸载／更新产物和随包运行时按发行产物保存或发布。交付前核对 `git ls-files` 与忽略规则，不能因整个目录被忽略而漏掉安装逻辑。
- 目录内提供可实际使用的安装、卸载和更新入口，复用工具已有机制。安装包可兼任升级包，卸载入口调用安装时注册的卸载器，并核对目标安装实例。按实际构建结果组织文件，不强制生成三个独立 EXE 或占位入口。
- 使用有效的既有构建链；新项目可采用 Electron Forge 或合适的成熟打包工具。锁定实际依赖并维护唯一安装入口；更新优先复用已有发布渠道和成熟更新器，不为换工具重建项目或另造独立更新服务。
- Windows 进程名称与图标应体现项目身份。通过现有构建链为实际承载界面的 EXE 设置项目名称、`FileDescription`、`ProductName` 和项目 ICO。从日常入口启动，在任务管理器“进程”页确认分组名称和图标，同时核对实际进程路径。
- Electron 源码运行需要上述身份时，可在依赖准备阶段生成项目专属运行文件，沿用已有轻量启动器。修改 Electron EXE 文件名时配套重命名 WER 崩溃报告库，例如 `MyApp.exe` 对应 `MyApp_wer.dll`，并确认实际启动的运行文件及配套库一致。
- Windows 应用提供可双击的安装程序，并注册到“已安装的应用”供用户卸载。安装包交付应用和启动所需的运行时、业务依赖，用户安装后可从正常入口启动。本地后端及其运行时随安装交付，使用远端服务时明确必要配置。源码开发继续使用项目独立环境。
- 安装式产品将配置和数据库放在用户可写的应用资料目录，凭据沿用项目已有的受控存储。Electron 可使用 `app.getPath('userData')`，主题仍可用 YAML。程序资源不当作可写数据目录。便携模式明确保存位置与写权限，既有布局迁移按获批范围处理。
- 持久数据、配置、凭据和缓存按[程序与资料生命周期](application-lifecycle.md)保护。升级保留用户资产，卸载默认保留个人资料，清除个人资料须由用户明确选择。首次安装不能依赖维护者的绝对路径、私人配置或源码目录。
- **构建与发布分开。** 应用名称、图标、版本和安装说明与产物一致。用户要求本地验收时，可以交付明确标注的未签名安装包；正式签名、公证、证书购买、上传 GitHub 和公开更新按项目发布要求及用户授权执行。本地构建不自动上传或发布；在已要求正式交付的任务中，缺失的正式验收仍须说明。交付可双击的安装包、用户需选择的实际路径，以及进程身份、安装卸载、迁移、首次设置和更新的已验证／待验证步骤。

### Windows 安装、迁移与首次设置

以下为 2026-11-16 用户明确的交付要求，具体实现与实际验收记录由各项目维护。

- **安装目录可选。** 手动安装提供默认路径和可用的“浏览”按钮，允许选择 D 盘等有写权限的位置。覆盖安装预填已登记的原目录，保留原路径即可直接更新；手动更换目录时仍可浏览。安装器不得硬编码维护者的盘符或路径。需要把程序与项目放在一起时，可用项目直属的 `installed/` 存放已安装程序，并将 `/installed/` 加入项目 Git 忽略规则；它与交付源码 `installer/`、产物 `installer/dist/` 各司其职。
- **升级保留资料，换目录只留一份程序。** 程序目录与设置、数据库、报告及日志保持边界。覆盖安装和自动更新默认复用原程序位置、资料位置及凭据。用户明确改路径时，核对旧安装记录、目标写权限、新位置是否为空及是否与资料目录冲突，确认迁移后再执行。只处理确认属于该安装实例的旧程序，旧程序移除失败时停止迁移；成功后核对只有一份有效程序、一条安装记录，快捷方式指向新位置。迁移不顺带搬动或清理个人资料，卸载默认保留资料。
- **完成页进入基础设置。** 手动安装完成页默认提供“打开应用并进行基础设置”。打开后回显已有设置并允许调整主题；有 API 功能的项目可为现有配置填写密钥。密钥使用系统凭据存储，不回显原密钥明文，留空保留原值，允许跳过。默认沿用已有设置和历史数据，不把是否保留资料设成一道选择题。此入口只用于手动安装完成后的启动；自动更新重启后按原设置进入工作台，不再次进入安装向导。

使用 electron-builder v26 的 NSIS 时，手动安装需采用可交互向导（`oneClick: false`）并开启 `allowToChangeInstallationDirectory: true`；仍须实际检查新装与覆盖安装的目录选择页和“浏览”按钮，不能以配置项存在代替可用。手动安装向导与应用内一键更新分别实现和验收，不因手动安装需要选择目录而增加自动更新的交互步骤。

### 自动检查与一键更新

- **交付闭环。** 持续维护的桌面应用从首次安装版起交付自动检查与应用内更新。每个项目在现有发布说明或项目 Skill 中明确正式更新源、版本／渠道、目标平台、签名方式、构建发布入口和验收证据。发布新版本时，将安装包与匹配的更新清单一并交付到已授权的发布源；源或签名未就绪时列为交付缺口，不能以按钮存在代替可用。先用两个真实版本跑通安装、保留资料升级和卸载，再验收完整应用内链路；普通局部修复不自动扩大为已有项目的整套改造。
- **自动查，用户决定是否装。** 安装版启动后异步检查正式更新源，长期运行按项目确定的合理间隔复查，并保留“检查更新”入口。只向当前平台／架构提示更高的正式版本，版本比较复用工具能力。帮助菜单或设置入口显示小蓝点或等效提示及可用版本；检查只取更新信息，用户点击前不下载更新包。离线或检查失败不阻塞当前功能，手动检查区分“已是最新”“发现新版”和“检查失败”。
- **一次点击完成正常升级。** “更新并重启”一次确认后，自动下载并显示进度，验证发布清单中的包摘要和预期发布者签名，再完成关停、安装与新版重开；无需用户另找安装包或再次点安装、重启。沿用更新器防止重复下载／安装；系统要求的权限确认按实际权限处理，不绕过或承诺免除。
- **关停与资料保留。** 安装前沿用应用现有的保存编辑、任务收尾和自有服务关停流程，完成后再交给安装器；不能安全退出时说明阻碍并保留当前应用。不终止无关进程，不在取消退出后借普通关闭偷偷安装。新版必须沿用实际资料根与凭据来源，尤其保留用户自行选择的资料目录，不能悄悄切回默认目录。安装成功以新版实际启动、版本确认和原资料读回为准。
- **失败可继续使用或恢复。** 下载、摘要或签名校验失败时不执行安装器，保留当前应用与资料，给出清楚原因和重试入口。安装阶段失败按实际状态提供重新启动或重装等有效恢复入口，不将部分安装说成成功，也不承诺未经验证的自动回滚。
- **按工具版本实现。** Electron Windows 可用 NSIS 与 electron-updater，沿用已选构建链。electron-updater 6.x 对此交互应显式设置 `autoDownload = false`、`autoInstallOnAppQuit = false`，由检查、下载和安装接口驱动；其他版本按对应官方接口落实同一行为。`quitAndInstall` 的退出顺序不同于普通退出，保存和异步服务收尾须在调用前完成，并核对安装器实际重开方式。正式产物执行签名校验；未签名回环测试使用独立安装标识及隔离资料，不能混入正式发布或据此关闭正式校验。

## 6. 验证按本次变化选择

| 变化 | 应得到的证据 |
| --- | --- |
| 页面或交互 | 实际打开应用走受影响路径；检查关键状态、键盘、窗口缩放和对应截图，不能只凭 HTML／类型检查通过 |
| 主进程、IPC 或后端连接 | 从 UI 发起真实受控调用，核对返回、失败、任务结束及资源归属；必要边界用有意义的输入验证 |
| Windows 进程名称、图标或运行文件变化 | 从日常入口启动，检查任务管理器“进程”页的分组名称与图标，核对实际 EXE 路径和适用的 WER 配套库 |
| 首次打包、安装链或发布 | 从 installer/dist/ 的真实产物安装，在没有项目源码和 Conda 开发环境的测试环境核对主程序及本地后端启动、运行时来源、系统卸载入口和个人资料保留；用两个真实版本验证升级 |
| Windows 安装目录或安装流程 | 用实际安装包至少完成新装、原位覆盖、改路径迁移；操作默认路径／浏览、原目录预填、完成页和基础设置。核对主题、API 密钥留空保留／跳过、旧设置及历史读回；迁移后旧程序移除、安装记录唯一、快捷方式指向新位置，旧程序移除失败时不继续迁移；用隔离资料验证卸载只移除程序及登记 |
| 自动检查与提示 | 用两个真实安装包与受控更新源核对启动检查、周期复查和手动检查；显示新版及蓝点／等效提示，日志或请求记录证明点击前未下载更新包；离线不影响主功能，最新版本及检查失败有正确反馈 |
| 一键更新与资料保留 | 从已安装旧版点击一次“更新并重启”，核对下载进度、摘要／签名校验、编辑保存和自有服务正常退出、新版按原设置自动进入工作台及实际版本；读回原设置和历史数据，覆盖用户自选资料目录 |
| 更新失败与恢复 | 受控验证下载失败、摘要不符和签名无效时未执行安装、旧应用及资料仍可用且可重试；不能安全退出时不安装；安装启动失败按实际阶段提供有效恢复入口 |
| 正式发布与验证边界 | 分别记录回环双版本测试、正式签名及真实发布源下载／更新结果；正式清单、平台产物与版本对应，未完成项列为缺口，不将未签名本地测试推广为正式更新已可用 |
| 大表格、流式日志或性能变化 | 用代表性数据检查响应、滚动和资源占用；根据实际瓶颈采用限量渲染／虚拟化等，不预先堆优化层 |

普通小改动不重复整个安装矩阵；构建通过不等于安装通过，截图漂亮不等于功能可用。无法运行或缺少目标系统时明确缺口。用户保留的手动验收依[手动验收与升级保留](manual-install-validation.md)执行。

双版本升级可在隔离资料与回环发布源上验证。观察更新提示、下载时机、一次点击的安装与重启，再读回原有设置和数据。正式签名和公开发布源需各自的验证记录。
