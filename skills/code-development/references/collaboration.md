# 项目约定初始化、协作开发与 PR

适用：用户维护范围内持续开发或协作交付的项目，以及项目约定维护、任务分支、PR、评审、合并与 rebase。外部项目贡献沿用该项目已确认的流程，不自动植入个人约定。本文不授权建库或远程操作；按主文和当前任务授权执行。主分支指项目实际的默认／集成分支，以下 `main`、`origin` 均为示意，执行前核实。

## 1. 必须遵守的协作底线

1. **小而完整，便于审查。** 一个提交围绕一个清楚目的，PR 聚焦一个可说明和验证的任务；只修改必要职责，给重要逻辑段配少量准确注释。独立整理与功能修改尽量分开；不为行数上限把相互依赖的功能拆成无法运行的碎片。大改先划分可交付步骤，不在结尾才提交一整包无关变化。
2. **不制造测试和文档垃圾。** 复用现有测试目录、测试入口与说明文档；新增测试应能暴露具体行为错误，新增文档应有实际读者与长期用途。临时探针、运行日志、重复 README类似等文档、自动生成的总结与占位测试不提交；必要回归测试、接口说明、安装变更仍须维护。不设置测试数量、文件数量或覆盖率的凑数目标，不把“少文件”变成拒绝必要验证的借口。
3. **自己的任务分支 → PR → 他人评审 → 合并。** 不直接在主分支开发或推送，不通过本地合并后推主分支绕开 PR。默认一任务一分支、明确负责人，完成后下一任务从最新主分支新建。个人未合并分支按下文同步；共享历史例外必须说明原因。
4. **提交者实际验证，不能把运行责任转给评审者。** 运行受影响路径和项目适用检查，PR 写明实际命令／操作、结果和未覆盖处。功能开发至少走过对应真实功能；UI 改动实际打开并交互。纯文档或低影响修改做与风险相称的检查，不要求无关全量测试。生成测试文件、仅语法通过、模拟数据漂亮都不等于功能通过。
5. **不得通过削弱规则制造通过。** 不删断言、跳过失败用例或移除检查来掩盖缺陷；需求改变导致断言或流程确需调整时，解释原契约与新行为并接受评审。保护用户已有改动，不夹带凭据、个人配置、环境和无关大文件；项目明确管理的必要测试夹具或产物按既有策略处理。

这些要求适用于人工和 AI 产出。作者负责审阅自己准备提交的差异；AI 自评或生成一段“检查通过”不能替代实际验证及约定的人类评审。

## 2. 项目约定的适用范围与初始化

目标链路：个人 Skill 提供初始化方法 → 当前项目根 `AGENTS.md` 保存实际约定 → 随代码提交并按授权进入远程 → 协作者 clone／pull 后，从接入该项目的客户端读取。个人模板存在不等于项目已初始化。

先确认实际项目边界，读取当前任务适用的已有约定，再决定是否写入。读取约定、维护 AGENTS.md 和初始化 Git 是三项不同操作；已有 AGENTS.md 本身不授予改写权限。

| 当前任务／项目 | 处理 |
| --- | --- |
| 用户维护范围内，已确定持续开发或协作交付的项目 | 获批开发阶段在业务改动前补建缺失入口或补齐必要基线；暂时独自开发不免除这一要求 |
| 已有完整且适用的项目约定 | 读取并遵守，不重写、不追加同义模板 |
| 临时脚本、一次性分析、临时目录或外部仓库局部贡献 | 不自动新建 AGENTS.md、复制个人基线或 git init；有既有约定仍须遵守 |
| 阶段1、纯审查或只运行测试 | 对项目约定只读；发现相关缺口可简短说明，不自行扩大到约定维护 |
| 用户明确禁止改约定，或限定只改指定文件 | 完成获批的代码工作，不额外创建／改写 AGENTS.md，不因此停止已获准的小修复 |
| 用户明确要求初始化或维护约定 | 按指定目录与范围执行，不据此扩大到其它项目或 Git／远程操作 |

项目是否持续维护应依据任务、现有项目目标或明确交付要求，不能凭“有代码”“有 .git”就推定。信息不足时先沿用已有约定，完成已授权的局部工作；只有选择会实质影响当前交付时才澄清。跳过初始化且可能影响约定交付时简短说明原因，不为每个临时脚本生成清单。

确定需要初始化后执行：

1. **确认写入位置与已有内容。** 使用准确项目根目录，缺失则创建，存在则先查重并保留项目事实；不把上层混合目录当作代码项目根。
2. **将条款写进仓库。** 使用[项目开发与协作模板](../assets/project-collaboration.md)合并必要基线：最小精准改动、反过度防御、简短逻辑注释、用户修改保护、有效测试与文档、分支与 PR、实际验收及授权边界。根文件必须有实际规则，不能只列个人 Skill 名称、模板路径或一句“遵守全局规则”。同时保留项目目标、入口、验证命令和项目特有约定；不复制整套个人 Skill 或与该项目无关的配置。
3. **已有约定只补缺项。** 等价条款复用；不得整文件覆盖、重复追加、恢复用户明确删除的内容，或用模板替换项目事实。若现有明确规则与本次基线冲突，说明具体差异并按用户已授权范围处理；尚未获准的冲突只暂停相关条款，不静默削弱基线。暂时没有评审人不自动豁免 PR／他人评审要求，可以完成本地开发或获准创建草稿 PR，合并等待所需评审。
4. **保证离开本机仍完整。** 根 `AGENTS.md` 使用仓库中的真实文本文件，不链接到个人目录。必要项目内资料使用可随仓库提交的相对路径，不能依赖维护者的个人绝对路径、私人 Skill 或未入库文件。全部项目通用开发约定在根文件可读，较长项目专用流程可按需引用仓库内资料。现有 CONTRIBUTING／README 可简短指向该约定，不再维护一份平行规则。
5. **核对加载入口。** 标准文件名使用 `AGENTS.md`，不把 `AGENT.MD` 等拼写当作默认可发现文件。检查同目录 `AGENTS.override.md` 及相关子目录约定是否使共享基线缺失或冲突；保留有效特殊约定，不能只更新一个实际未生效的根文件。子目录继承根基线、只补局部约定，不要求每层复制全文；新建／修改子目录约定时也不得无授权取消基线。初始化或入口变化后重新读取最终生效内容，必要时用客户端诊断验证；当前会话不能假定自动重载。
6. **纳入 Git 并验收交付。** 新增／修改的 `AGENTS.md` 与必要项目内引用属于本次开发交付，核对是否被忽略，并随获批提交纳入版本。检查已跟踪路径、提交中的实际正文及相对引用；未提交、未推送、尚未合并分别如实说明，不能声称协作者已获得。初次建立传播机制时，可在隔离目录做一次本地 clone 并检查加载；不要求每个小改动反复 clone 或生成验证报告。目录未建库时按主文的 Git 初始化授权处理，不擅自将上层混合目录建库。

**模板必须填写项目事实。** 落地前替换模板中的主分支、验证入口和评审安排；写实际名称、命令或具体人工步骤，不留下占位符、示例值或“采用仓库实际名称”之类元说明。未建库写“尚未建库，无主分支”；未核实写“尚未核实”，不能伪装成“没有自动检查”。确认无自动检查时才写明该事实，并说明人工验证动作。评审人未确定则写“待指定”，不虚构账号或将其视为已批准。维护者明确保留的项目事实优先，不机械补一套字段。

普通后续开发读取并遵守已经完整的约定，不反复重写；这项准备不授权批量改写其它仓库。各客户端读取机制不同，Codex 的项目加载结果不能替其它模型作保证。

## 3. 分支生命周期与 rebase

### 开始与提 PR

- 确认仓库、当前分支、远程、差异和本次文件归属。自己的任务从最新主分支建立；如果工作已发生在主分支，先保留现有修改并把本次工作移到自己的任务分支，不用 reset／clean 丢弃内容。夹杂他人修改或分支关系不明时，只暂停受影响的历史操作。
- 在任务分支完成小而完整的提交和必要验证。用户已授权推送或创建 PR 时，核对目标远程和任务分支后推送；没有远程授权时停在本地交付。审查、推送、合并、强推和保护设置分别按已获授权范围判断，不因为流程图含有某一步就自动执行。
- PR 简短写清：问题与修改后的行为、主要改动、实际验证、已知限制。UI 改动按需附关键截图；涉及协议、依赖、数据格式和删除行为时注明影响。正文沿用仓库模板，不添加没有决策价值的十几项打勾表。

### 同步最新主分支

1. 获取远程最新状态，核对工作区和目标分支。更新本地主分支时保持快进同步，不在主分支 rebase；无法快进说明本地存在分叉，先弄清原因，不自动丢弃本地提交。
2. **自己的未合并任务分支，且没人依赖其旧历史时，推送／更新 PR 前默认 rebase 到最新远程主分支。** 常见动作是 fetch 后在任务分支 rebase 已核实的 `origin/main`；目标随仓库实际情况替换。冲突按真实业务解决，再运行受影响检查。
3. 不把裸 `git pull --rebase` 写成通用“同步 main”命令：它通常拉取当前分支配置的上游，可能只是远程同名任务分支。先分清“更新远程任务分支”和“以最新主分支为基底”。

### 共享历史例外与强推边界

| 当前情况 | 处理方式 |
| --- | --- |
| 仅自己提交，未发布，也无人基于该分支工作 | 默认 rebase 最新主分支，完成相关验证 |
| 已发布但确认只有自己使用，无下游依赖 | 可按默认规则 rebase；需改写远程历史时另核对强推授权及远程变化 |
| 有他人提交、他人基于该分支工作、堆叠 PR，或已被拉取且依赖情况不明 | 不擅自 rebase；先协调。保留共享历史时将主分支合入任务分支，或由相关人明确同意重排；在 PR 中写明例外原因和处理方式 |
| 他人的分支或主分支 | 不以整理历史、同步或减少冲突为由 rebase／强推 |

- 已发布个人分支确需强推时，明确授权目标与影响，核对远程当前提交且没有未纳入的他人改动，使用针对具体分支和预期远程提交的 `--force-with-lease=<ref>:<expected>`。禁止无保护 `--force`。租约失败说明远程变化，先检查差异，不直接刷新预期值后重推。
- 普通 `--force-with-lease` 依赖远程跟踪引用，可能受后台 fetch 影响；它不是“不覆盖别人工作”的无条件保证。租约保护也不能替代对他人下游分支的协调。
- 分支名称属于自己，不代表其历史没有被别人依赖。使用例外时在 PR 简述原因；不把例外扩大为“所有分支永远不 rebase”，也不为线性外观覆盖共享工作。

### 评审、合并与下一任务

- 至少由一位具备相应能力和项目权限、非作者的评审者批准，阻塞问题解决且必要检查通过后，才按获批范围合并。新修改应让评审覆盖最终待合并差异；失效批准不能作为通过依据。
- 作者不能自批自己的 PR；已得到必要他人批准并具备合并权限时，可以由作者执行合并。批准资格与合并执行者是两回事，遵守仓库实际设置与任务授权。
- 合并后及时获取最新主分支；本地主分支只做快进更新。完成的任务分支不继续承接下一任务，尤其 squash merge 后，新提交可能不共享原分支的提交身份，复用易带入旧差异或冲突。
- 下一任务从最新主分支新建；同时进行的其它个人未合并任务分支仍按上面的 rebase／共享例外规则同步。停用旧分支不等于立即删除，删除本地或远程分支按仓库策略及授权执行。

## 4. 用平台权限落实底线

AGENTS.md 管理约定，平台保护控制能否绕过。实际配置须针对具体仓库获得授权；写下要求不代表已配置成功。

- 对主分支配置规则集或分支保护：必须经 PR、至少一次适当的非作者批准、必要状态检查通过、阻塞讨论解决；禁止强推和删除，限制可绕过人员。不要为了方便给所有协作者管理员或绕过权限。
- 防止“批准后追加未经审查代码”：按平台设置使过时批准失效，或要求最近一次可审查推送由其他人重新批准，结合风险决定。不盲目要求两个重叠机制同时开启。
- 只把已有且能稳定发现问题的检查设为必需；按项目实际运行 lint／类型检查／构建／关键测试等，不能要求不存在的检查，也不先搭一整套与项目无关的 CI。没有可用 CI 时明确人工验证与平台门禁的差距。
- 将协作约定、CI 和 CODEOWNERS 的变更纳入维护者评审。GitHub 可用 CODEOWNERS 指定这些文件的负责人，并配套必需 Code Owner review；单独添加文件不会自动强制审批。按平台实际权限确认，不能让同一个 PR 轻易删掉自己的验收门槛。
- 核对托管平台、仓库可见性、套餐、维护者权限与绕过设置。平台能力不足时说明缺口，可采用收紧主仓库写权限、fork PR 与维护者合并等已批准流程；不声称仅靠提示词能硬性阻止 push。
- 验证先读取实际配置、匹配分支和检查记录；若要证明拒绝行为，仅在获批的一次性测试仓库演练，不通过向真实主分支推测试提交来试保护。

## 5. 倡导项

- 用简短分支名说明负责人或任务；命名格式沿用项目，不强制统一英文前缀。
- 较大任务尽早开草稿 PR，先看职责和方向；把可独立审查的机械整理与功能修改分开，但不为形式拆分紧密相关修改。
- 审查优先关注正确性、必要性、真实验证和维护成本；风格交给已有工具，不用个人喜好阻塞合理实现。
- 提交说明遵循主文和项目约定；及时回应评审、同步主分支。功能开关、预备重构、复杂提交规范只在确有项目需要时采用。
- 团队需要追溯 AI 辅助时，可在 PR 简短注明工具及其参与范围；只记录实际已知信息，不猜模型版本，不把工具署名当作验证或责任转移，也不默认添加固定提交前缀。
