## 代码开发与协作约定

- 本约定适用于整个项目和所有贡献者，个人独立开发也遵守。开始工作前读取根与当前目录适用的 AGENTS.md；子目录规则继承本基线、补充局部要求，未经维护者批准不得削弱。新增或更新项目约定时保持仓库内自包含，并随代码纳入 Git，不能只依赖个人全局设置。
- 每个提交目的清楚，PR 聚焦一个可验证任务，改动尽可能小而精准。复用现有职责和依赖，不夹带无关整理；主要逻辑段用少量简短注释说明行为，保持注释与代码一致。
- 不为假想需求新增抽象层、参数或防御分支。新增校验、异常捕获、重试或回退须对应真实输入、契约或恢复需求；真实权限与数据边界仍须处理，不吞异常或以默认值伪装成功。
- 保留用户已有代码和文字取舍，不恢复其明确删除的说明，不覆盖其重写。只有本次行为改变确实需要时补充必要说明，不顺带整理无关文件。
- 复用现有测试与文档入口，只增加能验证具体行为的测试及必要说明。不提交临时探针、重复 README、模板化总结或占位测试，不以文件／测试数量证明质量。保护用户已有修改，不夹带凭据、个人配置、运行环境及无关产物。
- 保持项目根目录精简，保留必要入口、README／AGENTS、依赖与工具配置及既有一级目录；文档、测试和脚本优先归入已有对应位置，必要新目录须有明确用途。不在根目录堆放临时草稿、排查脚本、自动报告或另建杂项目录，隐藏目录也不例外。临时产物使用已有临时位置或系统临时目录，收尾只清理本次创建且不再需要的临时项；用户指定位置和工具链要求优先，不擅自迁移或删除既有无关文件。
- 在自己的任务分支开发，推送任务分支并发起 PR，至少一位合适的非作者评审者批准、必要检查通过后才合并。不在主分支开发、直接推送或用本地合并绕过 PR。
- 提交者必须实际运行受影响功能及项目适用检查；UI 修改实际打开并操作，纯文档修改做相应检查即可。PR 写明问题与结果、实际验证及缺口；生成测试文件或只通过静态检查不能冒充功能通过。不靠删断言、跳过用例或关闭检查掩盖失败；契约确需改变时说明并接受评审。
- 推送／更新 PR 前，获取最新主分支，自己的未合并且无人依赖的任务分支默认 rebase 到它。裸 `git pull --rebase` 不保证同步主分支。若有他人提交、下游分支或共享依赖不明，先协调，必要时将主分支合入任务分支，并在 PR 写明例外原因；不擅自改写他人或主分支历史。
- 个人已发布分支确需改写历史时，先确认授权、远程提交及协作依赖，使用带明确预期提交的 force-with-lease；租约失败先核查，不无保护强推。合并后及时同步最新主分支，本地主分支只快进更新；下一任务从最新主分支新建，尤其不复用已 squash 合并的旧任务分支。
- 评审须覆盖最终差异，AI 自评不能代替他人批准。作者取得必要他人批准后可按权限与授权合并。协作约定、CI 和审批规则的变更须由维护者审查，不通过同一改动绕过验收。
- 文档不代表远程保护已启用。平台保护、必需评审和检查以已核实配置为准；配置缺口明确说明。Agent 默认只提交本地，推送、创建 PR、合并、强推及保护设置均按任务已获授权范围执行，不因本文自动扩大权限。
