# 代码开发与审查

本技能提供 AntTrail 的开发默认约定。桌面交付、主题与 Python 环境是可按项目调整的偏好，以使用者明确的技术栈与交付目标为准。

## 适用方式与工作流程

- 开始时确认本次目标、工作模式及授权范围；
  核对仓库、已有差异及当前生效的项目 AGENTS.md，定位相关代码、调用关系及已有测试，
  按条件性参考表选读必要资料。
- 已有项目约定须读取并遵守；仅对用户维护范围内、持续开发或协作交付的项目，
  默认按[项目初始化与协作](references/collaboration.md)补建／补齐 AGENTS.md。
  临时脚本、一次性分析及外部仓库局部贡献不自动初始化；只读任务不写入。具体判断见参考第 2 节。
- 实现、修复或重构：在正确职责处完成必要修改，
  运行相关验证并审阅最终差异，按下文 Git 约定收尾。
- 仅运行测试：按授权范围执行相关检查并报告结果，不要求产生代码修改或提交。
- 代码审查：确认审查对象、范围和比较基准，
  查看差异及判断行为所需的调用、契约和测试；
  报告有依据的问题、位置、触发条件及影响，不制造问题。
  未经另行授权，不修改、修复或提交审查对象。
- HTML 功能或训练代码任务可结合当前环境已有的相关 Skill；本技能不依赖其他 Skill 才能使用，也不因相关技能存在就加载其全部流程。

## 最小精准改动：实现选择的最高优先级

- 在满足本次明确需求、正确性和项目既有约束的前提下，
  将改动小、落点准、实现直接作为方案选择的最高优先级。
  优先降低理解、审查和维护成本，不以架构完整、功能通用或形式漂亮为额外目标。

- 修改前先确认问题对应的现有职责、调用关系和可复用能力。
  优先在正确的现有位置直接修正，或复用已有实现；不另造一套平行机制。
  这些是方案选择的优先方向，不要求逐级试错，也不能为了少动文件把逻辑塞进错误位置。

- 新增文件、函数、参数、配置、依赖或处理分支，都应服务于当前任务中的具体需要。
  无实际调用者的接口、所有调用处取值相同却无独立用途的参数、
  无人设置的配置和仅为未来预留的分支，默认不添加。

- 保持项目根目录精简，新增根级文件或目录须有明确职责，优先放入已有合适位置。
  根目录保留项目必需的入口、元数据／工具配置及一级目录，例如 README、AGENTS.md、LICENSE、
  依赖清单与锁文件、约定的主程序／EXE 入口，以及 src、tests、docs 等；沿用现有命名和布局，不机械套目录白名单。
  不在根目录随手创建临时草稿、一次性排查脚本、自动总结／验证报告或含义不明的目录；
  能在回复或已有文档中说明的，不另建文件。长期文档、测试和脚本优先归入已有对应位置，必要新目录须有明确用途；
  临时产物使用项目已约定的临时位置或系统临时目录，不为一个临时产物再造根级杂项目录，隐藏目录也不例外。
  收尾只清理本次创建且确认不再需要的临时项；用户指定的交付位置和工具链要求按实际需求保留，
  不以本规则为由迁移、删除既有无关文件或重构整个目录。

- 没有明确的架构设计需求，不新建框架、通用基类、工厂、策略层、插件机制或多层包装。
  不把简单条件判断改造成一组类，不为一次调用增加仅负责转发的层次，
  不以“以后可能扩展或复用”为理由提前设计通用方案。

- 小函数可以用于清楚表达当前职责、隔离复杂逻辑或消除实际重复；
  但抽取后应确实更容易理解，不能只是把同一段复杂度分散到更多位置。
  不为满足函数行数、文件数量或抽象层级等形式指标而拆分代码。
  不为追求复用而强行合并语义不同、只是表面相似的逻辑。

- 优先使用项目已有依赖和语言标准能力。
  现有代码能够直接完成的操作，不另加工具库、通用辅助模块或可配置子系统；
  确需新增时，应有当前需求和实际收益支持。

- 除本次目标明确要求外，保持公共接口、默认值、返回结构、异常语义、
  执行顺序和副作用不变。不以简化为由悄悄改变兼容性或业务行为。
  不用密集单行、嵌套表达式或隐蔽技巧换取更少行数。

- 每个修改片段都应对应本次实现、缺陷修复、必要验证或必要说明。
  不顺手改名、重排、格式化、优化或整理无关代码。
  只清理由本次修改新产生的无用内容；既有无关问题不自动处理。

## 反过度防御：没有具体用途就不添加

- 新增校验、异常捕获、重试、回退或兼容分支前，先从项目文档示例、受支持的输入、现有调用方或真实数据中定位触发路径。
  对照代码、接口契约或明确需求判断该路径的预期行为，只在现有处理不足时补上。确认问题可达就应指出，无须等到故障发生。
  若新分支只为处理上一层兜底制造的状态，优先修正引入该状态的那一层。

- 区分真实边界与内部契约。
  外部输入违反格式或业务约束，是可能需要处理的真实情况；
  已由当前实现或明确契约保证的内部条件，不在后续每层重复检查。
  不仅凭类型注解就认定外部数据可信，也不为普通内部调用建立通用验证框架。

- 不用动态属性探测、宽泛类型转换、空值替换或多种字段名尝试，
  把必需字段缺失、类型错误或内部不变量被破坏伪装成正常情况。
  解析、转换和兼容只覆盖项目实际支持的输入、格式、协议与版本。

- 只有本层确有恢复、资源处理、契约要求的错误转换或必要诊断上下文时，
  才新增异常捕获。已有上层处理足够时，沿原有机制传播。
  不逐层捕获、重复记录后再抛出，不为每次 I/O 机械添加异常包装。
  资源清理优先沿用既有上下文管理或清理机制。

- 不捕获所有异常后返回空列表、空对象、零值、False、None 或成功状态，
  让失败看起来像正常结果；这些值只有在既定业务语义中才可作为结果。
  不为使流程继续而吞掉程序错误、必要依赖缺失或权威数据读取失败。

- 默认值、降级和回退必须有明确业务含义。
  必填配置缺失时不自行猜值；当前算法失败时不擅自切换另一算法；
  当前实现报错时不悄悄调用旧实现。
  应修复失败原因，或按既有约定清楚暴露失败。

- 不默认增加重试、缓存兜底、恢复状态机或多套备用路径。
  确需重试时，检查依赖或上层是否已经重试，并明确可重试原因和停止条件；
  重复执行可能产生副作用时，必须符合项目已有的安全执行约定。
  不在多层叠加重试，也不对明确的参数错误、权限错误等盲目重试。

- 不新增无人使用的校验文件、状态标记、追踪记录或恢复信息。
  哈希、校验和与指纹仅用于明确要求，
  或替代明显更昂贵且其结果会影响后续处理的操作。

- “不新增无依据防御”不等于“删除所有既有防御”。
  已有检查用途尚未查明时，不认定它无用；只在本次范围内，
  确认相关契约和行为后才删除或简化。
  用户、项目及更高优先级指令要求的安全、数据保护、迁移、验证和审查仍须完成。

## 可读性与注释：以逻辑段的行为说明为主

- 注释语言遵循项目明确约定；无特别约定时默认使用简短中文。

- 对本次新增或修改的、有独立处理目的的主要逻辑段，
  默认补充少量简短注释，帮助读者快速理解该段在做什么。
  逻辑段按处理职责划分，不按空行、固定行数或每条语句划分。

- 注释首先概括本段的整体行为、数据转换或业务目的；
  必要时再补充不明显的原因、约束、顺序依赖和副作用。
  不把“注释只能解释为什么”作为通用限制，忽略读者理解代码行为的需要。

- 输入整理、核心计算、重要分支、状态更新和外部写入等主要步骤，
  应能通过代码结构和就近注释看清处理过程。
  不能仅笼统声称“代码自解释”，就省略复杂逻辑段所需的说明。

- 优先将简短说明放在对应逻辑段之前或紧邻相关语句的位置；
  不强制行尾注释，不逐行翻译代码，不用长篇文件头或 docstring
  代替局部行为说明。项目明确要求的接口文档仍按约定保留。

- 单句操作、清晰命名已充分表达的简单片段，可以不加注释。
  避免“初始化变量”“遍历列表”“返回结果”等没有补充信息的机械说明，
  不设置注释覆盖率，不为补齐注释而切碎代码或新增辅助函数。

- 注释应准确、简短，与它解释的代码保持一致。
  行为改变时同步维护相关说明，不保留失真的旧注释；
  不写变更流水、模板化口号或与当前实现无关的解释。

- 只维护本次涉及的代码与注释。
  用户对文字的明确删改优先，不以注释覆盖或风格统一为由，
  恢复用户删除的说明、覆盖其重写，或补回同义内容。

## 用户编辑与文字维护

尊重用户对文档、CHANGELOG 和代码注释等文字的编辑取舍，其明确删改优先于 Agent 旧稿、模板及本 Skill 的通用写作要求。后续以当前文件为基础，不恢复已删除内容，不覆盖用户重写，也不变相补回同义表述。新改动确实需要更新说明时，仅补充必要的新事实，沿用用户的简洁程度；未被用户修改的内容不视为已审核认可。

## 条件性流程

- 面向用户安装使用的应用统一通过安装程序交付，安装后的应用及本地后端使用随包运行时，从应用入口直接启动。持续维护的桌面应用从首次安装版起，将自动检查新版、版本提示及应用内一键更新纳入必需交付，按下列桌面交付参考实施与验收。项目根目录使用 `installer/` 管理安装、卸载与更新的源码、脚本和配置，构建产物放入该目录的产物区并按发行产物管理。源码开发和测试仍可使用项目独立 Conda 环境。具体目录、Git 范围和验收见[桌面 UI 与应用交付](references/desktop-ui-and-app-shell.md)。

## 验证与交付

- 修复缺陷时，优先编写或使用能暴露原问题的测试，先确认失败，再验证修复；确实无法复现时，说明证据及验证边界。
- 新增输入验证时，检查实际支持输入中的无效情况及预期处理；不扩展为任意构造输入的穷举。
- 重构时，运行相关检查并比较修改前后的行为，确认需要保留的行为未变。
- 按改动影响的调用方选择能发现实际行为错误的检查。共享接口、数据格式或持久状态变化时，覆盖依赖它们的主要路径。
  对可逆、低影响改动，不为形式新增测试，也不写只复述实现或匹配代码措辞的用例。
- 优先使用项目已有的相关测试、构建或静态检查。同一代码版本和输入条件下，已有实际运行验证过同一路径的目标行为时，复用其结果。
  检查失败先判断是否与本次改动有关，不自动修复无关故障。必要检查通过后交付，仅在有新改动、失败或仍有具体疑点时追加检查。
- 交付前按上述实现与注释规则审阅差异，修复本次引入的问题并完成受影响检查；
  已授权范围内不逐项索取批准，不扩展无关改动，也不生成形式化报告或无实际用途的测试。
- 报告实际运行的检查及其结果；未运行、受阻或未覆盖的部分如实说明，不将静态检查或模拟结果表述为实际运行通过。

## Git 迭代与提交

- 持续维护或协作交付的代码项目使用 Git；已有仓库修改前核对根目录、分支和差异，区分本次任务与用户原有内容。临时脚本、一次性分析和临时目录不因本技能自动建库。
- 项目约定的随仓库交付及分支／PR 流程按[项目初始化与协作](references/collaboration.md)执行。
- 需要新建 Git 仓库时，在计划中说明准确项目目录和纳入内容，该范围获批后再初始化；创建 AGENTS.md 不等于获准 git init，不擅自将上层目录或大型混合目录建库。
- 在获批代码迭代完成必要验证后，仅提交本次相关改动；暂存前检查实际差异，避免夹带无关文件、凭据或大数据与权重。不为凑齐提交而撤销用户改动。
- 提交说明用简短、具体的中文，保留必要技术名词和用于定位的实验 ID；默认不加 emoji、多重方括号标签或固定的机器／Agent 前缀。记录实际分支与提交号，默认只提交本地；远程 push 须有明确授权，用户已要求推送任务分支或创建 PR 时不重复确认。PR 授权不自动包含合并、强推或修改仓库保护规则。
- 普通提交和实验不自动创建 Git tag；只有用户明确要求时才创建。消息中的标签与 Git tag 分开处理，不为统一新规范改写历史提交或自动删除已有 tag。
- 审查任务不默认产生修改或提交。训练前后代码、配置和结果摘要的专门提交门槛，按该训练任务的明确要求执行。
